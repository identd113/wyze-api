# Release notes: wyze-api 2.0.0-beta.3

The changelog is written for people using the library. This page is for whoever ships and supports it: what changed in the code, what has been checked on real hardware and what has not, and what is known to be unfinished.

**Compared against:** `v2.0.0-beta.2` (`e313ab3`, published 2026-08-29), the last published release. An earlier staged build of `2.0.0-beta.3` (before the thermostat and error-redaction fixes) was rejected and never published, so the number is unused. This release is `35` commits and `62` files on top of `beta.2` (`+5,213 / -704` lines). Always compare against the last published release, not against the last commit or a branch.

**Pairs with:** `homebridge-wyze-smart-home@2.0.0-beta.3`.

## Breaking changes

- **The constructor throws when `username` is empty.** It used to fail later, at login. Code that builds a client without credentials must handle the error.
- **Node.js 22 or newer.**
- **Thermostat setpoints are whole degrees Fahrenheit.** `setThermostatHeatingSetpoint` and `setThermostatCoolingSetpoint` took tenths (`680`) in beta.2 and now take `68`. Values outside 40-100 are rejected with a message that says so, which also stops a value written in the old unit from reaching the device.
- **`setIotProp`'s parameter is `deviceModel`** (it was `product_model`). Positional callers are unaffected.
- **Login and token errors no longer contain the Wyze response.** The text of "Invalid credentials", "Failed to refresh access token", the unsupported-MFA error and the bad-request error now goes through `sanitizeLogMessage`.

## New public API

| Method | What it does |
|---|---|
| `cameraWarmUp(mac, model, { label, ttlMs })` | Opens a WebRTC connection ahead of a stream and keeps it. A live stream takes it over. |
| `cameraWarmSnapshot(mac)` | A JPEG from the open connection's latest keyframe. |
| `cameraWarmDown(mac)`, `cameraWarmState(mac)` | Close the open connection; read its state. |
| `prefetchCameraConnection(mac, model)` | Fetch the signaling details ahead of a stream. |
| `cameraGetEventsMulti(macs, { sinceMs, count })` | The cloud event list for several cameras in one request. |
| `cameraGetEvents(mac, { sinceMs, count })` | One camera; built on the above. |
| `cameraGetDeviceMgmtState(mac, model)` | `{ on, available, siren, floodlight, notify, motion }` for devicemgmt cameras. |
| `cameraUsesDeviceMgmt(model)`, `cameraIsDoorbell(model)`, `cameraSupportsPowerControl(model)` | Synchronous checks by model. |
| `closeAllCameraSessions()` | Closes every open camera session. |
| `destroy()` | Stops the token refresh timer. |
| `getCameraSnapshotImage(mac, { deviceModel })` | The new option skips a device-list request. |
| `startCameraHKStream(...)` handle: `isAlive()` | False once the stream stopped or gave up reconnecting. |

Constructor options: `totpSecret` (new), `mfaCode` (restored). Documentation for the warm-connection methods is in the changelog only; the README and wiki do not describe them yet.

## What changed in the code

### Camera streaming (`src/devices/cameraStreamCapture.js`, `cameras.helpers.js`)

- **Codec objects per session.** werift numbers payload types by mutating shared codec objects, so after one stream with audio, later sessions got video payload type 98 instead of 96 while the SDP handed to ffmpeg said 96. ffmpeg then ignored every packet: snapshots timed out and live views went to "video idle". Codecs are created per session and the video SDP names the payload type the camera negotiated.
- **Audio.** Wyze answers PCMU/8000 under a dynamic payload type; the SDP for ffmpeg only listed 0 and 111. `extractAudioCodec` names the negotiated type. A camera that negotiates audio but sends none continues video-only.
- **Parameter sets.** `captureStreamFrame` holds the incoming RTP until the camera's SPS/PPS are known (from the answer SDP, or from the RTP), starts ffmpeg with them, replays the held packets and keeps asking for a keyframe. SPS/PPS are remembered per camera so ffmpeg can start before the first packets arrive; a session that started on remembered values follows the camera's fresh ones.
- **Keyframes.** Detection sees fragmented IDR slices (`keyframeTracker.js`); the first keyframe is held until ffmpeg is running (`videoHold.js`), and a keyframe handed to a stream gets SPS/PPS in front of it when it has none.
- **Audio reordering** (`rtpReorderBuffer.js`): late or out-of-order packets are put back in sequence; a packet that never arrives becomes 20 ms of silence. In-order audio adds no delay. A lab test with 3% loss and 60 ms jitter dropped the "missed packets" warnings from 15 to 0.
- **Ports.** Local UDP ports for ffmpeg are remembered for two minutes and only handed out when the neighbouring RTCP port is free. A capture is retried once with fresh details if ffmpeg still loses the race.
- **Sessions.** At most one per camera. A new one waits until the previous has fully closed (peer connection first, awaited); a capture never preempts a live stream; a failed start releases everything.
- **Reconnect.** A stream whose reconnect fails is retried up to 4 times with a growing delay; a connection that stays up for 30 s resets the budget.

### Devices and routing

- New models registered as cameras: Cam Pan v4 (`HL_PAN4`), Doorbell v2 (`HL_DB2`), Floodlight v2 (`HL_CFL2`). Bulb Cam (`HL_BC`) light uses `run_action` `floodlight_on` / `floodlight_off`.
- `cameraSpotLight`, `cameraFloodLight`, `cameraSiren`, `cameraPrivacy` and `cameraNotifications` route devicemgmt cameras (`LD_CFP`, `AN_RSCW`, `GW_GC1`, `HL_PAN4`) to the devicemgmt API and leave other models as before. Per-model property lists are in `src/util/devicemgmtProps.js`.
- The Doorbell v2 cannot be powered off through the API (`run_action power_off` answers `result: 3`).

### Login and tokens

- `totpSecret` (`src/util/totp.js`): RFC 6238 code on every login; waits out a nearly expired or reused window; retries once with the next window, only when Wyze answered without a token. Pasted values are cleaned (spaces, dashes, quotes, invisible characters, `otpauth://` links) and a malformed one fails with a clear message that does not echo it.
- 2FA login restored (`mfaCode`); it had been dropped in the Feb 2024 "Clean up MFA" commit.
- A stale saved token no longer blocks re-login. Tokens are kept on a transient refresh failure (network error, timeout, 5xx) and cleared only when Wyze rejects them. The file is written owner-only (`0600`).
- The refresh timer fired every ~2.9 minutes (seconds where milliseconds were required); it is now 48 hours. Concurrent `refreshToken()` calls share one request.

### Housekeeping

- Two unused duplicate signer helpers were removed from `src/utils/crypto.js`.
- The combined publish workflow was replaced by beta and stable workflows, both using `npm stage publish`.
- Log levels: the per-request "API rate limit remaining" line and the video ffmpeg messages are at `debug`. The warning for a nearly exhausted limit is unchanged.
- `docs/camera-properties.md` (what each camera property is, and how we know) is new.

## What has been checked, and how

### Checked on real hardware (test bridge)

- Snapshots and live video through the plugin on Cam v3 and Doorbell v2 cameras; the snapshot capture produced a JPEG in about 4 s on 6 of 6 tries on two cameras.
- Doorbell v2 audio, video at 640x480 / 15 fps, the cloud event list, and the fact that power-off is refused.
- Startup pictures from the final build on the Front Doorbell and the Back Yard Cam.
- Floodlight on a Cam v3 (through the plugin).

### Unit tests only

TOTP and login, token persistence, RTP reordering, port allocation, the warm connection, session exclusivity, the capture retry, thermostat setters, error redaction. `npm test`: 325 pass, 1 skipped.

### Not verified on hardware

- 2FA login against a live account.
- Cam Pan v4, Bulb Cam and the devicemgmt cameras (ported from SecKatie/wyzeapy).
- Doorbell v2 power, siren and notification writes, and a doorbell press.
- The thermostat setpoint unit (whole degrees). It matches what the plugin has always done, but there is no thermostat on the test bridge.
- The units of `temperature` and of Room Sensor (`CO_TH1`) readings.

## Known issues

- Back Yard Cam audio does not reach the player; unresolved (`docs/camera-properties.md`).
- `P1048` is probably sound-event recording; unconfirmed.
- `getHmsID()` returns the raw plan list. It is documented as a wrapper around `getPlanBindingListByUser()`.
- Three near-duplicate walkers of the STAP-A response in `cameraStreamCapture.js`.
- The wiki repository does not exist yet, so the `wiki-sync` workflow fails until the first page is created.

## Releasing

1. The release is built from `2.x`.
2. The `NPM_TOKEN` secret is a stage-only token. Run the `npm publish (beta)` workflow (or create a GitHub release with Pre-release ticked, tag `v2.0.0-beta.3`); it stages the version.
3. Approve the staged version on npmjs.com with 2FA (or `npm stage approve`).
4. Verify: `npm view wyze-api dist-tags` shows `beta` at `2.0.0-beta.3` and `latest` still at `1.1.15`.
5. If an earlier staged build of this version is pending, reject it first (`npm stage reject <id>`); a staged version reserves the number.
