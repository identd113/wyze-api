# Release notes: wyze-api 2.0.0-beta.4

The changelog is written for people using the library. This page is for whoever ships and supports it: what changed in the code, what has been checked on real hardware and what has not, and what is known to be unfinished. The notes of the first `2.0.0-beta.4` attempt, [2.0.0-beta.4-first-attempt](2.0.0-beta.4-first-attempt.md), describe the part of this release that was tagged on 2026-11-02; read them too.

**Compared against:** `v2.0.0-beta.3` (published to npm 2026-10-26), the last published release. This release is 84 commits and 125 files (+8,095 / -857 lines for the 109 files that are not documentation, the changelog or the lockfile) on top of it. The first `v2.0.0-beta.4` was tagged and released on GitHub on 2026-11-02, but its npm publish was never approved, so it never reached npm; its GitHub release and tag were then deleted and the number reused here. Commits after that tag include the 429 wait, the `totpSecret` deprecation, the Floodlight v2 experiment, the SDP files in `persistPath/tmp` and the four review fixes below.

**Pairs with:** `homebridge-wyze-smart-home@2.0.0-beta.4`, whose `dependencies.wyze-api` is `^2.0.0-beta.4`. Release `wyze-api` first.

## Breaking changes

None added by this release. The 2.x line stays a drop-in replacement for 1.1.15 (`tests/compat-1x.test.js`); the new methods and exports are additions. The first-attempt notes list the one behaviour change that carried over (`cameraWarmUp` leaves a camera alone while a live stream of it is open).

## New public API (since the last published release)

- `getCameraNightVision(mac)` returns `"on"`, `"off"` or `"auto"`; `setCameraNightVision(mac, value)` sets it and reads it back (`{ before, after, matches }`). Local network only (the camera must have the `dtls` flag, an IP and its keys in the device list). One conversation per camera at a time through an internal queue (`_oneAtATime`), which the test page also uses.
- `createCameraTestServer(options)` and `validateWebPort(port)` (lazy exports): the browser page for cameras. Options let the host give it a read-only `settings` view, a read-only `sensors` view, an `unsupported(device)` check with `describeDevice(model)` and `versions` for the Other devices tab, an `issueForm` for the prefilled GitHub link, and stand-ins (`probe`, `setNightVision`, `deviceReport`) for tests.
- `src/deviceReport.js` (`buildReport`, `ENDPOINTS`, `scrub`, ...): the read-only device report shared by `scripts/device-report.js` and the page. Each entry records the endpoint each answer came from.
- `src/tutk/client.js`: a pure-JavaScript local camera client (discovery, DTLS with the ECDHE-PSK ChaCha20 suite, AV login, K-command authentication, night vision, a whitelist of read-only get commands). No native library. The older native TUTK and GUTES code stays in `future/`.
- `scripts/device-report.js` (`--local`) and `scripts/camera-test-web.js` (`npm run camera-test`).
- The camera test page's sidebar shows the Wyze Smart Home logo (embedded, so the page's policy now allows `img-src data:` and nothing else), links to the project home and the issue chooser, and the plugin, `wyze-api` and Node versions. `createCameraTestServer` fills these from its `versions` option.
- Plus the additions listed in the first-attempt notes: `getPropertyListForDevices`, `getCamPlusPlans`, event `types` and `tags` filters and `ageMs`.

## What changed in the code

- **The page** (`src/web/`): `cameraTestServer.js` (routes, access rules, one test at a time, the token lockout), `cameraTestPage.html` (one file; tabs for Cameras, Other devices, Sensors and Settings; no inline script or style outside the nonce), `issueLink.js` (the prefilled issue link, trimmed to fit in a URL). Access: a private-network client only, no proxy headers, a Host check, an Origin check, a random token compared in constant time; 20 wrong tokens block an address for 10 minutes. A page that has been refused once stops asking.
- **The device report** only calls `getDeviceList`, `getPropertyList`, `getDeviceInfo` and `_deviceMgmtGetIotProp`, through a view of the client that throws on anything else, and scrubs MAC addresses, names, IP addresses, Wi-Fi names, ids, serial numbers and similar keys by key name and by shape. Firmware and hardware versions are kept on purpose.
- **Local camera client:** the DTLS handshake records its first ClientHello in the transcript (a HelloVerifyRequest restarts it), timers are cleared on every exit, and a challenge the camera answers with too little data is an error, not a crash.

## Quality and care

- **Tests:** 445 pass, none skipped. A test loads the page's script and fails on any name it uses that is not defined, and another fails if the page uses anything its content security policy blocks. The page's server has tests for every route, the access rules, the lockout, one-at-a-time and the queue.
- **Review:** a code review of everything in this release. Its findings (a gap in the one-test-at-a-time guard, a lockout after a restart, the test page bypassing the per-camera queue, a leaked timer in the local client, the report scrubber missing some keys, the issue "kind" for room sensors) were fixed.
- **Privacy:** test fixtures use made-up MAC addresses; a real camera's MAC that had been used in two tests was replaced before anything was pushed.

## Since the first beta.4 attempt (tagged 2026-11-02)

- **Rate limits:** a 429, or a 503 with `Retry-After`, to a Wyze host is waited out and retried (`src/util/rateLimit.js`). A small `X-RateLimit-Reset` is read as seconds from now. How Wyze limits (per account, endpoint or host) has not been measured.
- **`totpSecret` is deprecated:** accepted, warned about once, never used. A login with only the API key worked on a 2FA account here; `mfaCode` still works as a one-time code.
- **Floodlight v2 (`HL_CFL2`):** the light is switched through devicemgmt first and falls back to `P1056` with a warning (plugin issue #16). A guess; nobody here owns the device and the reporter has not tested this build.
- **ffmpeg SDP files** are written to `<persistPath>/tmp` instead of the OS temp folder.
- **Review fixes:** the lock `crypt_secret` no longer reaches debug logs, a refresh refused with error 2001 no longer hangs the client, and the device report reads Wyze's real property-list envelope.

## What has been checked, and how

### On a real account and home network

- Local sessions: authentication, night vision read and set (with read-back) on a Doorbell v2 and a Cam v2; reads on two Cam v3. All four cameras have the `dtls` flag.
- The page, served inside Homebridge on the test bridge: cameras, the Other devices list (five devices), a report for one device (property list and device info answered; no MAC or IP address in it), read-only settings and sensors.

### Unit tests only

- The Other devices flow with stand-in clients, the long-report summary in the issue link, errors, and the queue.

### Not verified

- A report for a camera with a devicemgmt answer through the page, and a local session through the page for an unsupported camera.
- Night vision write on a Cam v3, and on any battery camera.
- The Floodlight v2 devicemgmt write, and the 429 wait against a real Wyze rate limit.
- Cameras on the Gwell protocol (OG, Pan v4) cannot be reached by the local client.

## Known issues

- A camera serves a few sessions; a local conversation can interrupt a viewer in the Wyze app.
- The report's scrubbing is by key name and shape, so an unusual field could carry a personal value; the page and the issue form tell the reader to look before submitting.
- `npm run tutk-smoke` and `fetch-wyze-sdk` still belong to the parked native code in `future/`.
